# 点位拖拽保存与阀室联动方案

> 目标：在地图拓扑页拖动点位后，能够直接保存到数据库；全国统一视图重新加载后自动使用新坐标；同时对受影响的阀室坐标进行联动更新，避免只动一个站点、整条线上的阀室仍停留在旧位置。

---

## 1. 需求背景

当前地图拓扑页已经支持：

- 拖动节点位置
- 在前端内存里记录改动坐标
- 重新渲染当前页面的拓扑点线

但还没有形成真正的业务闭环：

1. **拖完没有真正保存到库里**
2. **全国统一视图虽然能从后端重新取数，但前端没有在拖拽保存后完成统一刷新**
3. **阀室数量很多，而且很多阀室是沿着干线/支线顺排的，主站位置改了，阀室如果不跟着更新，就会出现整条线几何形状断裂、折线不自然的问题**

所以这次方案要解决的不是单纯“加一个保存按钮”，而是要把下面三件事一次打通：

- 地图拓扑页拖点即保存
- 全国统一视图自动同步新坐标
- 相关阀室按规则联动调整

---

## 2. 现状梳理

### 2.1 前端现状

地图拓扑页 `src/views/MapTopologyView.tsx` 已经有：

- 拖拽后记录 `dirtyPositions`
- `dragend` 时把新坐标写回 `baseTopoNodes`
- 页面级重新渲染

说明：

- “拖完能看到效果”这一步已经有了
- 但“拖完写库 + 其他视图同步”这一步还没接上

### 2.2 后端现状

后端 `backend/app/routers/topology_editor.py` 已经有坐标保存接口：

- `PUT /api/topology/station/{station_id}/position`
- `PUT /api/topology/stations/batch-position`

说明：

- 后端保存能力已经存在
- 当前缺的是前端调用、联动更新规则、缓存刷新和阀室批量调整策略

### 2.3 全国统一视图现状

全国统一视图 `src/views/GlobalPipelineView.tsx` 使用的是：

- `loadAllPipelines()`
- 后端 `/api/pipeline-packages`

这意味着：

- 只要数据库坐标变了
- 并且前端管线缓存失效了
- 全国统一视图重新加载后就能看到新位置

### 2.4 阀室数据现状

系统里的阀室不是少量虚拟点，而是数据库中真实存在的大量 `Station(type='valve')` 记录。

当前确认到：

- `stations` 表总数约 1215
- 其中 `valve` 约 871

所以这次方案必须认真设计“阀室怎么联动”，不能只处理主站点。

## 3. 目标定义

本次功能目标分三层：

### 3.1 用户体验目标

用户在地图拓扑页操作时，希望流程是：

1. 拖动一个点位
2. 点击保存，或者开启自动保存后直接落库
3. 全国统一视图再次进入时看到同样的新位置
4. 相关阀室不再留在原来的旧位置，而是一起被合理带动

### 3.2 数据一致性目标

要保证以下几个视图看到的结果一致：

- 地图拓扑页
- 全国统一视图
- 其他依赖 `pipeline-packages` 的视图

### 3.3 几何合理性目标

当用户移动“主控制点”时：

- 不能只改一个点
- 受影响区段上的阀室要保持相对顺序和相对分布
- 避免出现“主站点 moved，但中间阀室全留在原位”的断裂感

---

## 4. 推荐方案总览

推荐采用 **“主点手动编辑 + 阀室自动跟随 + 支持阀室单独锁定”** 的三层方案。

### 核心原则

- **非阀室站点**：默认允许人工拖拽，是几何修正的主控制点
- **阀室点**：默认不建议单独自由漂移，而是跟随其所属区段自动重算
- **被人工明确单独调整过的阀室**：标记为“锁定”，后续主点变化时不再自动覆盖

这是一个兼顾“可控”和“不会越修越乱”的方案。

---

## 5. 为什么不能直接用“全量平移”

最容易想到的方案是：

> 一个主站点动了多少，附近阀室就整体平移多少。

这个方案实现简单，但问题很多：

- 如果一段线两头的主站都改过，全量平移会互相打架
- 阀室会整体漂走，破坏它们沿线均匀分布的关系
- 支线接入点附近会越来越乱

所以不建议用“统一偏移量”做最终方案。

---

## 6. 推荐算法：区段插值联动

### 6.1 基本思想

把一条干线或支线看成由多个节点串起来的顺序链路：

- 压气站 / 分输站 / 门站 / 枢纽：主控制点
- 阀室：中间跟随点

当某个主控制点坐标变化后，不是简单挪动相邻一个阀室，而是重新计算这个主控制点所在“区段”上的所有阀室位置。

### 6.2 什么叫“区段”

一个区段定义为：

> 从一个非阀室主点出发，沿着管线往前找，直到下一个非阀室主点为止，这中间夹着的一串阀室，组成一个区段。

例如：

```text
压气站A -> 阀室1 -> 阀室2 -> 阀室3 -> 分输站B
```

这一整段就是一个区段。

### 6.3 重算规则

对于区段中的每个阀室，记录它在区段中的相对位置比例 `t`：

- 靠近起点越近，`t` 越小
- 靠近终点越近，`t` 越大

当区段两端主点坐标变化后，阀室按新起点和新终点重新插值：

```text
新阀室位置 = 新起点 + t * (新终点 - 新起点)
```

这样会带来三个好处：

- 阀室顺序不乱
- 阀室仍然均匀分布在新线段上
- 两端主点都改了也不冲突

## 8. 功能设计

## 8.1 前端交互设计

### 模式一：手动保存（推荐先做）

在地图拓扑页加一个保存区：

- 显示“已修改 N 个点”
- 提供“保存坐标”按钮
- 提供“撤销未保存改动”按钮
- 提供“保存时联动阀室”开关（默认开启）

优点：

- 不容易误操作
- 用户可以连续拖多个点后一次保存
- 适合生产环境先上线

### 模式二：自动保存（第二阶段）

后续可以再加：

- 拖动结束后自动延迟 500~800ms 保存

但不建议第一阶段就上，因为：

- 用户频繁拖拽时会产生很多请求
- 阀室联动重算是批量操作，不适合每拖一下都立即提交

**建议：第一期先做手动保存，第二期再考虑自动保存。**

---

## 8.2 保存请求设计

建议不要直接复用现在最简单的 `batch-position` 接口做全部逻辑，而是新增一个带语义的接口：

### 新接口建议

`PUT /api/topology/positions/commit`

请求示例：

```json
{
  "updates": [
    { "id": "WE1-179", "longitude": 120.8701, "latitude": 31.2702 }
  ],
  "cascade_valves": true,
  "cascade_scope": "segment",
  "preview_only": false
}
```

字段说明：

- `updates`：用户手动移动过的点
- `cascade_valves`：是否联动阀室
- `cascade_scope`：联动范围，建议默认 `segment`
- `preview_only`：是否只预览、不真正落库

响应建议返回：

```json
{
  "updated_station_ids": ["WE1-179"],
  "updated_valve_ids": ["WE1-180", "WE1-181"],
  "updated_junction_ids": [17],
  "affected_layers": ["we1", "cred", "jxlz"]
}
```

这样前端保存后就知道：

- 哪些主点被保存了
- 哪些阀室是系统自动联动改的
- 哪些枢纽中心会变化
- 哪些视图数据需要刷新

---

## 8.3 阀室联动范围设计

这里是核心设计点。

建议分三种范围：

### A. `none`

- 只保存用户手动拖动的点
- 阀室不动

用途：

- 调试
- 特殊修补场景

### B. `segment`（推荐默认）

- 只重算该点所在区段上的阀室
- 不影响整条干线其他无关区段

这是最稳妥、最符合直觉的默认方案。

### C. `branch`

- 重算该点所在整条支线或干线上的阀室

这个范围更大，适合大规模几何校正，但第一期不建议默认开启。

**建议默认值：`segment`**

---

## 8.4 阀室锁定机制

为了防止系统自动重算把用户精修过的阀室位置覆盖掉，建议给阀室增加位置状态：

### 建议新增位置元数据

存到 `stations.properties` 里，避免立刻改表结构：

```json
{
  "positionMeta": {
    "mode": "auto",
    "locked": false,
    "segmentStartId": "WE1-179",
    "segmentEndId": "WE1-184",
    "ratio": 0.42,
    "lastManualAt": null
  }
}
```

字段说明：

- `mode=auto`：系统自动计算
- `mode=manual`：用户手动调过
- `locked=true`：后续联动时不覆盖
- `segmentStartId / segmentEndId`：它归属哪个区段
- `ratio`：它在区段中的相对位置比例

### 锁定规则

- 普通阀室默认 `auto`
- 如果用户单独拖动某个阀室，就自动切换成 `manual + locked=true`
- 后续主点变化时，跳过这个阀室

这样既能联动，也保留人工精修能力。

## 9. 后端实现方案

## 9.1 新增服务层

建议新增：

`backend/app/services/position_commit.py`

职责：

1. 接收前端提交的点位更新
2. 保存主点新坐标
3. 识别受影响区段
4. 计算需要联动的阀室列表
5. 重算阀室坐标
6. 更新枢纽中心相关影响
7. 提交事务
8. 返回变更摘要

---

## 9.2 区段识别算法

区段识别建议按管线拓扑做，不按名称猜。

### 识别步骤

对于每个被拖动的非阀室节点：

1. 从该节点出发，找到相连的 `Pipeline`
2. 沿每个方向向外遍历
3. 遇到 `valve` 就继续走
4. 遇到下一个非阀室节点就停止
5. 收集这中间所有阀室，形成一个受影响区段

### 结果示例

```text
区段1：WE1-179 -> WE1-180 -> WE1-181 -> WE1-184
```

其中：

- `WE1-179`：主点起点
- `WE1-180/181`：阀室
- `WE1-184`：主点终点

---

## 9.3 阀室重算算法

建议优先采用“按原区段顺序 + 比例插值”的方案。

### 算法输入

- 区段起点新坐标
- 区段终点新坐标
- 区段中所有阀室原顺序
- 每个阀室的 `ratio`

### 算法输出

- 每个阀室的新经纬度

### 比例来源

第一期可以这样做：

- 如果 `properties.positionMeta.ratio` 已存在，直接用它
- 如果还不存在，就按区段内顺序平均分配
  - 例如 3 个阀室，比例分别是 `0.25 / 0.5 / 0.75`

第二期再升级为：

- 根据 `Pipeline.length_km` 或业务里程数据，按真实里程比例计算 `ratio`

---

## 9.4 枢纽联动

因为枢纽节点是多个站点坐标的中心点，所以任何成员站点或成员阀室变化之后，相关枢纽显示中心也会变化。

这里不建议单独存枢纽坐标，继续保持现在的策略：

- 枢纽中心在打包时根据成员站点实时计算

这样可以避免双写问题。

---

## 9.5 事务与缓存刷新

保存成功后，需要做三件事：

1. 数据库提交事务
2. 刷新拓扑服务缓存
3. 让前端管线缓存失效

建议后端保存成功后：

- 调用 `TopologyService(session).refresh()`

前端保存成功后：

- 调用 `invalidatePipelineCache()`
- 当前拓扑页保留已更新位置
- 全国统一视图下次加载时自动使用新数据

---

## 10. 前端实现方案

## 10.1 地图拓扑页新增保存区

在 `MapTopologyView.tsx` 加一个“坐标保存”模块：

- `已修改 0/3/8 个点`
- `保存坐标`
- `撤销未保存`
- `联动阀室` 开关
- `只预览影响` 按钮（可选，第二期）

### 保存流程

1. 用户拖动一个或多个点
2. `dirtyPositions` 记录待保存坐标
3. 点击保存
4. 请求后端提交
5. 成功后清空 `dirtyPositions`
6. 调用 `invalidatePipelineCache()`
7. 如有必要，重新执行 `loadAllPipelines()` 或提示“全国视图已同步”

---

## 10.2 当前页即时反馈

保存成功后建议给用户明确反馈：

- 已保存主点：3 个
- 已联动阀室：18 个
- 已影响枢纽：2 个
- 全国统一视图下次进入将自动使用新位置

这样用户会知道这不是只改了眼前一个点，而是整条相关区段一起改了。

---

## 10.3 全国统一视图同步策略

全国统一视图不建议做复杂的“增量局部补丁”，第一期保持简单：

- 统一走 `invalidatePipelineCache()`
- 重新从 `/api/pipeline-packages` 取最新包

原因：

- 当前系统的数据源已经统一到后端 API
- 坐标变化、枢纽中心变化、线段路径变化都能一起刷新
- 实现简单，风险最小

## 11. 推荐上线顺序

## Phase 1：最小可用版本（建议先做）

目标：先把“拖点保存 + 全国视图同步”做通。

范围：

- 地图拓扑页增加“保存坐标”按钮
- 前端调用批量保存接口
- 保存成功后失效管线缓存
- 全国统一视图重新取最新数据
- 暂时不自动联动阀室，只给出影响提示

优点：

- 上线快
- 先把主流程打通
- 风险小

缺点：

- 阀室仍可能留在旧位置

---

## Phase 2：区段级阀室联动（推荐主版本）

目标：解决用户现在最关心的问题。

范围：

- 新增 `positions/commit` 接口
- 后端识别区段
- 自动重算受影响阀室位置
- 保存结果返回影响摘要
- 前端显示联动结果

这一步完成后，功能就基本可用了。

---

## Phase 3：阀室锁定 + 预览模式

目标：让几何修图能力更专业。

范围：

- 阀室支持手工单独锁定
- 保存前支持预览影响范围
- 支持 `none / segment / branch` 切换
- 支持操作日志与回滚

---

## 12. 风险点与应对

## 风险 1：一个点连接多个方向

比如枢纽或分输站可能同时接多条线。

应对：

- 按“方向区段”分别处理
- 不做整个网络的全局平移

## 风险 2：阀室被人工精修过

应对：

- 增加 `locked` 机制
- 自动联动时跳过锁定阀室

## 风险 3：旧数据没有比例信息

应对：

- 第一版按区段顺序平均分布
- 后续补真实里程比例

## 风险 4：前端频繁保存导致请求太多

应对：

- 第一版采用手动保存，不做拖完即自动提交

## 风险 5：跨视图看到的结果不一致

应对：

- 保存后统一失效 `pipeline` 缓存
- 所有视图继续只认 `/api/pipeline-packages`

## 14. 推荐决策

如果现在要快速推进，我建议你拍板采用下面这套：

### 第一阶段决策

- 拖点后 **手动点击保存**
- 保存接口采用 **批量提交**
- 全国统一视图通过 **缓存失效 + 重新取包** 同步
- 阀室联动策略默认采用 **segment 区段插值**
- 阀室先不开放任意自由拖动，避免几何越修越乱

### 这是为什么

因为这套方案：

- 开发量可控
- 风险低
- 能直接解决你现在提的核心痛点
- 后面还能继续扩成“阀室锁定 / 预览 / 自动保存”

---

## 15. 一句话总结

> 这次不是做一个“拖点后存坐标”的小功能，而是要把“主点修图 → 阀室跟随 → 全国统一视图同步”整条链路做成一个完整能力。推荐先上“手动保存 + 区段级阀室联动”的版本，最稳、最实用。
