## 3. 验证方法

## 3.1 后端联动验证

为了避免直接改动正式数据，本次验证采用了“**同 Session 内模拟提交，但不真正落库**”的方式：

- 使用 `PositionCommitService.commit(...)`
- 临时把 `session.commit()` 替换成空操作
- 在内存态里完成：
  - 主点坐标更新
  - 阀室联动更新
  - 全国包重新取数

这样能验证逻辑是否跑通，同时不污染数据库。

### 验证目标点

本次选用：

```text
WE1-1 轮南压气站
```

模拟把它移动到新位置后，检查：

- 主点是否变化
- 阀室是否被联动
- `/api/pipeline-packages` 的结果里是否已经是新坐标

---

## 3.2 前端构建验证

执行：

```bash
npm.cmd run build
```

目标是确认本次前端改动不会导致构建失败。

```text

PACKAGE_VALVE ('西气东输一线干线', 84.58666665609138, 41.78416666702845)
```

### 结果解释

这组结果说明了几件事：

#### 1）主点保存逻辑生效

`WE1-1` 的坐标从：

- `(84.25, 41.78)`

变成了：

- `(84.27, 41.795)`

说明主点坐标更新逻辑正常。

#### 2）区段识别逻辑生效

系统识别出的受影响区段为：

```text
WE1-1 -> WE1-7
```

并找到了该区段内的阀室：

- `WE1-2`
- `WE1-3`
- `WE1-4`
- `WE1-5`
- `WE1-6`

说明“沿主点所在区段收集阀室”的算法正常。

#### 3）阀室联动重算生效

至少有一个阀室 `WE1-2` 的坐标已经变化为新值：

```text
WE1-2 -> (84.58666665609138, 41.78416666702845)
```

说明不是只改主点，而是阀室联动也确实执行了。

#### 4）全国统一视图数据源同步生效

`pipeline-packages` 里读取到的结果已经是新坐标：

- 主点 `WE1-1` 在包里的坐标变成 `(84.27, 41.795)`
- 阀室 `WE1-2` 在包里的坐标也变成联动后的新值

这说明：

> 只要真实保存成功，并且前端做缓存失效，全国统一视图就会使用这次新坐标。

## 8. 当前仍需注意的点

虽然主链路已经跑通，但还有几个后续优化点：

### 1）目前更偏向“主点驱动”

当前方案最适合：

- 拖主站点
- 阀室自动跟随

如果后面要支持“阀室单独精修后不再自动覆盖”，建议继续做“阀室锁定”。

### 2）当前比例策略仍可继续加强

现在区段联动采用的是“按区段顺序 / 距离比例插值”的稳妥方案。

后续如果要更精确，可以再结合：

- 真实里程
- 支线结构
- 更精细的折线几何

### 3）当前验证是模拟提交，不是人工 UI 全流程录屏验证

本次验证证明代码链路已经通了，但如果要做最终上线确认，建议再做一次人工页面操作验证：

1. 打开地图拓扑页
2. 拖动一个主点
3. 点击保存坐标
4. 切到全国统一视图
5. 检查主点和相关阀室是否同步变化
