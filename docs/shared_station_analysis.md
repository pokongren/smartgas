# 合建站方案分析报告

## 1. 背景与定义
**合建站 (Shared Station)** 指在物理空间上为同一个站点，但在逻辑业务上服务于多条管线（干线或支线）的节点。在可视化系统中，合建站应被渲染为一个单一的图元，并能够展示其关联的所有管线信息。

## 2. 现状分析

### 2.1 数据现状
通过对现有数据库表 `node_relation_details` 的分析（基于 `analyze_shared_stations.py`）：
- **总站点记录数**: 3500+
- **同名站点数**: 349 个（涉及多条管线）
- **主要类型**:
    - **阀室 (Valve Rooms)**: 大量出现（如 "1#阀室" 关联 24 条管线）。相关性极高，但风险极大。
    - **压气站**: 如 "中卫压气站" (7 条管线)、"广州压气站" (4 条管线)。
    - **分输站**: 如 "永清分输站" (9 条管线)。

### 2.2 潜在风险：同名不同址
目前数据库中 `node_relation_details` 表**缺乏经纬度坐标信息**。仅依靠“站点名称”来识别合建站存在极高风险：
- **高风险案例**: "1#阀室"、"2#阀室" 等。不同管线的 "1#阀室" 往往位于完全不同的地理位置（例如湖南管网的1#阀室与中俄东线的1#阀室相距甚远）。若简单按名称合并，会导致地图上出现错误的连接飞线。
- **低风险案例**: "中卫压气站"、"广州压气站" 等具有唯一地名的站点，通常确实是同一个物理站点。

## 3. 解决方案建议

为准确识别和展示合建站，建议采取以下分级处理方案：

### 方案 A: 引入坐标系统的严格匹配 (推荐)
**逻辑**: 只有 **名称相同 且 坐标接近 (<50米)** 的站点才认定为合建站。
**需求**:
1. 必须完善数据库，导入每个站点的经纬度数据。
2. 数据清洗阶段，对同名但坐标不同的站点，在 ID 上做区分（如 `valve-1-hunan` vs `valve-1-russian`）。

### 方案 B: 建立合建站白名单 (短期替代)
**逻辑**: 针对特定类型的站点（压气站、枢纽分输站）建立白名单，仅对白名单内的同名站点进行合并。
**规则**:
- **合并**: 站点名称包含 "压气站"、"枢纽"、"储气库" 或特定地名分输站。
- **不合并**: 站点名称包含 "阀室"、纯数字编号。

### 方案 C: 拓扑分析
**逻辑**: 如果两条管线在拓扑数据中明确标识了互联关系（如 "中贵线" 与 "西三线" 在 "中卫" 互联），则将该节点视为合建站。

## 4. 前端展示方案
在地图视图中，合建站不仅是视觉上的合并，还需在交互上支持多维度信息展示：
1. **聚合标记**: 使用特殊图标（如双环图标）表示该站为合建站。
2. **多管线信息**: 详情面板 (ClusterDetailPanel) 需列出该站所属的所有管线名称。
3. **管线切换**: 用户可在详情面板中切换查看该站在不同管线下的属性（如不同管线的进出压力可能不同）。

## 5. 结论
鉴于目前缺乏坐标数据，**严禁直接全量按名称合并站点**，否则会导致严重的管网拓扑错误。
**立即行动项**:
1. 优先获取并导入站点坐标数据。
2. 在数据迁移脚本中，增加对 "阀室" 类通用名称的排重保护（即不合并）。
3. 仅对明确的 "压气站" 和 "枢纽站" 进行名称合并。
